UI Pattern Inventory & Standard Page Pattern

Every routed page in the tenant workspace and the Platform Management Portal, grouped by the shape it takes rather than the job it does — so pages that share a shape can be made to share a look, and pages that are genuinely one-of-a-kind can be explicitly exempted.

📅 29 July 2026 🌿 frontend/src 🧩 45 routed pages · 8 patterns 📐 18 index · 5 detail · 7 exempt 🔗 Follows up F-6 / F-7 / F-8 / F-9 / F-11

00  Executive summary

The pages look different from each other for one reason, and it is not the one you would expect. The design system is not missing — it is almost entirely unused. frontend/src/components/ already holds the right eleven primitives, written in June with explicit "new code should prefer this" comments. Adoption then stalled: <Button> has zero importers while 98 surfaces hand-roll a primary button, and <Table> has two importers against 28 raw <table> elements.

02  Pattern taxonomy

Eight shapes cover all 45 routed pages. P1–P3 are the "table of things → open one" family the review was aimed at; they are one pattern with three body treatments, not three patterns.

P1
Index — table → detail
Header + toolbar (search / filter) + table + optional pagination; row click opens a detail route.
9
P2
Index — card / row list
Same skeleton, but rows are multi-line cards carrying inline actions. No detail route.
4
P3
Index — edit in place
The row is the editor: expand or inline-save. No detail route.
5
P4
Entity detail
Wayfinding + identity header + status + KPI/summary + tabbed or stacked panels + destructive actions.
5
P5
Entity form
Header + single-column field stack + submit / cancel footer.
5
P6
Settings / config surface
Stack of labelled panels, each saving independently.
7
P7
Tabbed dashboard
Header + segmented tabs, each tab an independent data view.
3
P8
Bespoke canvas  exempt
Full-bleed or app-inside-a-page. Owns its own layout and scrolling. Adopts the frame and header only.

05  Proposed standard

5.1 · One page frame, owned by the shell

Delete every per-page mx-auto max-w-* and p-*. Width becomes a declared intent, not an accident of which page you copied from.

// AppShell keeps px-4 py-6. <Page> owns mx-auto, the cap, and vertical rhythm.
<Page width="standard">   // max-w-5xl — index, form, detail (default)
<Page width="wide">       // max-w-6xl — dense tables, dashboards
<Page width="full">       // no cap    — board, canvases
<Page width="bleed">      // no padding — map surfaces

SettingsLayout drops its own px-4 py-6 in the same change, which fixes the triple-pad.

5.2 · Three page templates

<IndexPage> — covers all 18 P1/P2/P3 surfaces

<Page>
  <PageHeader title subtitle actions />        // one type scale, always
  <Toolbar search filters right={viewToggle} /> // FilterChip only; no bare <select>
  <AsyncBoundary query={q}                       // one component owns the ladder
                 empty={<EmptyState message action />}  // action REQUIRED (F-8)
                 skeleton="table" | "rows">
    <DataTable columns rows onRowClick />       // or <RowList> for P2
  </AsyncBoundary>
  <Pagination />                               // rendered iff total > pageSize
</Page>

<DetailPage> — covers all 5 P4 surfaces

<Page>
  <PageHeader above={<Breadcrumb />}            // the ONE wayfinding idiom
              title subtitle badge
              actions={[edit, …, destructive‑last]} />
  <StatusBanner />                              // optional, role="status"
  <KPIRow />                                    // optional
  <Tabs /> → <Card> panels                     // SegmentedControl, never hand-rolled
</Page>

<FormPage> — covers all 5 P5 surfaces

<Page width="standard"> + <Breadcrumb> + one shared <Field> (label / help / error / required) replacing the seven local copies + a sticky <FormFooter> with cancel-then-submit ordering.

5.4 · Enforcement — the part that has failed before

  • ESLint no-restricted-syntax: ban raw <table>, raw <h1>, className="btn*", className="card", and the literal rounded-xl border border-ap-line bg-ap-panel outside src/components/.
  • Import guard (same mechanism as the existing lint-imports whitelist): page modules may not declare a component named Card, Field, or Row.
  • A page-template gallery — Storybook or an in-app /labs/patterns route — so "what does an index page look like" has exactly one answer to point at in review.

06  Theme

The token layer is sound. ap.* in tailwind.config.ts is coherent, and RTL is genuinely handled through tailwindcss-rtl plus logical utilities. It needs three additions, not a redesign.

1 · Type scale as tokens

text-page-title, text-section-title, text-body, text-meta — so writing text-2xl on an <h1> becomes unspellable rather than merely discouraged.

2 · Surface tokens

One radius, one border, one elevation. Today rounded-xl-no-shadow and rounded-lg-shadow-card both claim to be "the card", and both appear on the same detail page.

3 · Delete the dead palettes

brand-* is down to 2 uses; sand-* to LoginPage. Fold both into ap.* and remove the scales, or the next new page re-seeds the drift from the config file.

Dark mode is not in scope and nothing currently anticipates it. If it is wanted, the ap.* tokens must move to CSS variables during this pass rather than after it — retrofitting later means touching every file a second time.

08  Open decisions

Seven choices need to be made before phase 0 can be specified. The first four have visual consequences and are rendered side by side in the companion mockup deck.

1 · Row navigation

Whole-row click (the Platform convention) or a link in the identity cell (the Farms convention)?
Recommend both: <Tr interactive onClick> plus a real <Link> in column 1, so keyboard and middle-click survive while the whole row stays clickable.

2 · Filter idiom

Chips (TenantListPage) or dropdowns (DecisionTreeListPage)? Chips read better but do not scale past about six values, and DecisionTreeListPage has four axes.
Recommend chips for ≤2 axes and ≤6 values; a filter popover beyond that.

3 · Skeleton placement

Skeleton replaces the whole table (FarmListPage) or sits inside it, preserving the header row (TenantListPage)?
Recommend inside — the column headers stop shifting on every load.

4 · Detail-page composition

Tabs + KPI row (Platform) or stacked cards (Farms)? Both are defensible; they cannot both be the standard.
Recommend tabs once a page exceeds three panels, stacked below that — with the same header either way.

5 · Client vs server filtering

DecisionTreeListPage filters in a useMemo; TenantListPage filters server-side. <Toolbar> has to pick a default.

6 · Data layer

Are the 18 useEffect pages in scope for react-query conversion? Without it <AsyncBoundary> needs two shapes and half its value disappears.
Recommend yes, folded into each page's own conversion rather than as a separate sweep.

7 · Dark mode

In or out? Decide before §06, not after.
