Decision node — condition sources

Every source a decision node can branch on, and the two levels of fields beneath it. What each one means, where its data comes from, and what it resolves to when the data isn't there.

How a condition is built

Every comparison in a decision node has the same three parts:

PartWhat it is
LeftA value reference — a pointer at observed data. This is what the source picker and its sub-fields build. It is always data about the block being evaluated, never a literal.
Operator< ≤ > ≥ = ≠, plus between (a low/high pair) and in (a value list).
RightA literal (number, text, true/false) or a tree parameter reference, so the same tree can be re-tuned per tenant without editing its logic.
The rule that governs everything below: missing data fails closed. If a reference can't resolve — no imagery yet, no weather provider, a signal never recorded, a crop attribute the crop doesn't define — it evaluates to nothing, and the comparison is simply false. The node takes its on miss branch. Nothing is logged as an error, and nothing warns you. A predicate that can never be true is therefore indistinguishable, at runtime, from one that is merely false today. That is why each source below states when it is empty.
Numeric vs categorical matters. Fields marked number are compared with the ordering operators; fields marked text only make sense with =, ≠ or in. Comparing a text field against a number is always false — the builder now picks the right operand shape for you, but hand-written YAML can still get this wrong.
The nine sources
  1. Imagery index — satellite greenness, water, chlorophyll
  2. Block attribute — stage and soil
  3. Weather — observations, forecast windows, derived daily
  4. Weather index (anomaly) — curated indices vs climatology
  5. Disease / pest risk — modelled pathogen pressure
  6. Custom signal — your own recorded observations
  7. Grid anomaly — where inside the block the problem is
  8. Crop field — per-crop data on the assignment
  9. Tree parameter — right-hand side only

1. Imagery index indices

Satellite-derived vegetation and water indices for the block, from the most recent usable scene. This is the workhorse source: it is what "the crop looks stressed" means numerically.

  • Granularity per block
  • Updated each new scene (Sentinel-2, cloud-masked)
  • Needs an active imagery subscription on the block
  • Empty when no scene has been processed yet

Level 2 — Index code

CodeFormulaWhat it tells you
ndvi(NIR−RED)/(NIR+RED)Canopy greenness and vigour — the general-purpose health index. Saturates over dense canopy and is noisy where bare soil shows between trees.
ndwi(GREEN−NIR)/(GREEN+NIR)Surface water (McFeeters) — standing water, flooding, irrigation ponding. Not canopy moisture; that is ndmi. Higher means more open water, so its scale runs opposite to the vegetation indices.
eviMODIS 3-band formEnhanced vegetation index. Corrects for soil background and atmospheric haze, and keeps responding where NDVI has saturated — better for mature, dense orchards.
savisoil-adjusted, L=0.5Vegetation index that suppresses bright bare-soil background. The right choice for young, sparse or wide-spaced plantings and sandy reclamation land, where NDVI reads the soil as much as the crop.
ndre(NIR−RedEdge)/(NIR+RedEdge)Red-edge chlorophyll index — tracks nitrogen and chlorophyll status, and keeps discriminating in dense canopy where NDVI flattens.
gndvi(NIR−GREEN)/(NIR+GREEN)Green-band NDVI. More sensitive to chlorophyll concentration than NDVI, useful as a nitrogen proxy.
ndmi(NIR−SWIR1)/(NIR+SWIR1)Leaf and canopy water content (equivalent to NDII). Falls as the canopy dries, so it is the water-stress index — the one people often reach for ndwi expecting.

Level 3 — Key

KeyTypeMeaning
meannumberThe block's average index value on the latest scene. An absolute number, so thresholds have to be chosen per crop, per variety and per season.
baseline_deviationnumberThe default, and usually the right one. How far today sits from this block's own value for this day of the year, in standard deviations. Self-calibrating: ≤ −1.5 means "unusually low for this block at this time of year" whatever the crop. Needs enough history to have a baseline.
slopenumberRate of change over the recent history window, in index units per day. Negative means declining.
deltanumberTotal change across that window — the size of the move rather than its rate.
trend_directiontextThe trend as a word: rising, falling or stable. Lets a rule say "NDMI is falling" without picking a numeric cutoff.

Trend keys need enough recent scenes to compute; on a short history they resolve to nothing and the comparison fails closed.

2. Block attribute block

What state this block is in — its growth stage and its soil. Used to gate a tree so its advice only fires in the right context. This is the one source with no third level: pick the field and compare.

  • Granularity per block
  • All values are text — use =, ≠, in
  • Empty when the block has no current crop assignment

Level 2 — Field (no third level)

FieldMeaningValues
growth_stageThe block's current phenological stage, advanced automatically each day from the crop's stage calendar. The single most useful gate there is — it stops flowering advice reaching a block that is dormant.Per crop. Mango: pre_flowering, flowering, fruit_set, fruit_development, post_harvest_flush, veg_flush. Date palm: dormancy, pollination, fruit_set, kimri, khalal, rutab, tamar. Potato: emergence, vegetative, tuber_initiation, tuber_bulking, maturation.
soil_textureThe block's soil texture, recorded on the block record. Drives which index is trustworthy (bright sandy soil breaks NDVI) and how fast water moves.sandy, sandy_loam, loam, clay_loam, clay, silty_loam, silty_clay
salinity_classThe block's salinity banding, recorded on the block record. Gates salinity-aware advice such as leaching-fraction guidance.non_saline, slightly_saline, moderately_saline, strongly_saline
Crop identity is not in this list, deliberately. crop_category, crop_path and crop_strain were removed: a tree already declares which crop paths it runs on in Targeting, so branching on them inside the tree asks a question the targeting has already answered. If two varieties need different agronomy, give them two trees with different targeting rather than one tree that branches on its own crop.

3. Weather weather

Raw weather for the farm — what just happened, what is coming, and the derived daily roll-ups. The scope you choose decides which set of field names is available, and the three sets do not overlap.

  • Granularity per farm — every block on a farm sees the same numbers
  • Source the farm's weather provider
  • Empty when the farm has no provider or no rows in that window
The same quantity has three different names depending on scope. Maximum temperature is air_temp_c on the hourly observation (it is just "the temperature then"), air_temp_c_max across a forecast window, and temp_max_c on the derived daily row. Picking a name from the wrong scope resolves to nothing and the rule silently never fires.

Level 2 — Scope

forecast_24hThe next 24 hours of forecast, pre-aggregated into one row (sums, maxima, means).
forecast_72hThe same aggregation over the next 72 hours — for decisions with a longer lead time.
derived_todayToday's computed daily row: growing degree days, rolling rainfall totals, daily temperature extremes.
derived_yesterdayThe same row for yesterday — the only complete day, and so the honest one for "what did the crop actually experience".

4. Weather index (anomaly) weather_index

The curated weather-index family. Where the Weather source gives you raw numbers, these are the eight agronomist-defined indices, each with a built-in comparison against the farm's own day-of-year climatology. Ask "is this unusual here" rather than "is this above 35 °C".

  • Granularity per farm, daily
  • Empty when the farm has no projected index row for that day

Level 2 — Index code

CodeNameUnitMeaning
temperatureMax/Min Temperature°CDaily max / min / mean air temperature at the farm centroid. Heat drives evapotranspiration; cold suppresses photosynthesis.
radiationSolar RadiationW/m²Shortwave solar radiation, daily mean and total. High radiation lifts greenness indices and insect activity; low radiation favours fungal growth.
windWind Speed & Directionm/s, °Mean and maximum wind speed with vector-mean direction. Wind spreads fungal spores and disperses pests, and raises water demand.
humidityRelative Humidity%Daily mean relative humidity. Sustained highs drive powdery mildew and anthracnose — prolonged leaf wetness is the main trigger.
rainfallRainfall Amount & DensitymmDaily precipitation plus rolling 7- and 30-day totals. Heavy rain raises anthracnose and root rot.
evapotranspirationPlant Water Loss (ET₀)mmFAO-56 Penman-Monteith reference evapotranspiration, daily total. The demand side of the water balance.
evaporation_coeffSoil Dry-down / Water DeficitmmRolling 30-day sum of (ET₀ − rainfall): the cumulative soil water deficit. A stock — how dry the soil has become — as opposed to today's flux. Proxy for wilt and soil-larvae conditions.
rain_et_balanceRainfall ↔ ET BalancemmToday's water balance: rainfall − ET₀. Positive is surplus, negative is deficit. The daily flux whose running total is evaporation_coeff.

Level 3 — Key

KeyTypeMeaning
valuenumberThe index's actual value for the day, in the unit above.
baseline_deviationnumberThe default. The value as a z-score against this farm's climatology for that day of the year. ≥ 2 means "well above what this farm normally sees today". Needs several years of history for that day, and stays empty for indices whose spread is near zero in an arid climate (rainfall, often).

5. Disease / pest risk weather_risk

Modelled pathogen and pest pressure — the weather already interpreted through a disease model, so a rule can say "anthracnose pressure is high" instead of reconstructing temperature-and-wetness logic itself. Unlike the weather sources this is per block, because the model folds in the block's crop and growth stage.

  • Granularity per block, daily
  • Window a trailing 14 days of weather
  • Empty when the daily risk sweep hasn't scored the block
All three models are mango-only. A model only ever scores blocks whose crop sits under its registered crop. Branching on one of these from a tree targeting citrus or potato gives a branch that can never be taken. The picker now shows the crop in brackets and hides models your tree's crops can't be scored for.

Level 2 — Pathogen / pest

CodeCropWhat the model looks for
powdery_mildewmangoOidium mangiferae. Pressure builds on warm (about 20–27 °C), humid (RH above 60%) but dry days — free water on the leaf washes conidia off, so rain actually suppresses it. Worst through panicle emergence and flowering.
anthracnosemangoColletotrichum gloeosporioides. The mirror image: needs warmth (about 24–30 °C) and prolonged leaf wetness, from rain or near-saturated air. Accumulates through flowering and fruit development, often as latent infections that appear after harvest.
fruit_flymangoHumidity-weighted degree-day accumulation above a 13 °C development base, concentrated in the fruit-set and fruit-development window. Dry air damps the accumulation; the model is about generation speed, not a single day's weather.

Level 3 — Field

FieldTypeMeaning
scorenumberThe default. Accumulated pressure on a 0–100 scale. Use it when you want your own threshold.
leveltextThe same score banded into words: low (under 40), moderate (40–69), high (70 and above). Compare with = or in.

6. Custom signal signals

Your own recorded observations — anything your team measures that the platform doesn't: soil salinity readings, trap counts, lab results, a scouting verdict. The catalog is defined by your tenant, so this is the source whose vocabulary is yours rather than ours.

  • Granularity per block, from the latest observation that applies
  • Applies to a block if assigned tenant-wide, to its farm, or to it directly
  • Empty when nothing has been recorded for that signal

Level 2 — Signal code

Whatever your tenant has defined, listed by code. Each definition fixes a value kind when it is created, and that decides which key at level 3 will actually hold anything.

A definition also carries an aggregation mode. Where several observations fall in the window, the signal collapses to one value by latest, mean, median, max, min, sum or count. So "soil salinity" may mean the newest reading or the 30-day average depending on how it was set up — worth checking before you write a threshold against it.

Level 3 — Key

KeyTypePopulated when the signal's kind is…
value_numericnumbernumeric — a measurement. The common case.
value_categoricaltextcategorical — one of a fixed set of options defined on the signal.
value_eventtextevent — something happened, recorded by name.
value_booleantrue / falseboolean — a yes/no observation.
value_slopenumbernumeric only — rate of change over the trailing 30 days.
value_deltanumbernumeric only — total change over that window.
value_trend_directiontextnumeric only — rising, falling or stable.

Exactly one value_* key carries data per definition. Reading the wrong one for the kind always resolves to nothing — the picker now offers only the keys that can apply.

7. Grid anomaly grid

Where inside the block the problem is. The sub-block grid splits a block into cells and compares each cell against the block's own mean for that scene, so this source answers "is the weakness localised, and how bad is the worst patch" — the difference between a failing irrigation valve and a block-wide decline.

  • Granularity per block, per index
  • Needs a grid configured on the block
  • Empty when the latest scene crossed no threshold — present only when there is a current anomaly

Level 2 — Index code

The same seven imagery indices as source 1 — ndvi, ndwi, evi, savi, ndre, gndvi, ndmi — but read per cell rather than per block.

Level 3 — Field

FieldTypeMeaning
worst_znumberHow many standard deviations the worst flagged cell sits below the block's mean for that scene. The depth of the worst patch.
flagged_countnumberHow many cells crossed the detection threshold. The extent of the problem — one cell is a spot, twenty is a zone.
worst_rownumberGrid row of the worst cell. Position, for advice that needs to point somewhere.
worst_colnumberGrid column of the worst cell.
severitytextThe verdict for the block as a whole: warning or critical.

8. Crop field crop_attribute

The per-crop data recorded on the block's crop assignment — establishment method, transplant date, rootstock, tree age and whatever else the catalog defines for that crop. These are the fields that only make sense for one crop, which is exactly why they aren't columns on the block.

  • Granularity per block, from the current crop assignment
  • Vocabulary data, not a fixed list — it grows with the crop catalog
  • Empty when the block has no assignment, or no value was recorded

Level 2 — Crop field code

Defined per crop in the platform catalog and inherited down the taxonomy, so an attribute defined on mango is available to mango.keitt. The picker only offers codes that can resolve for the crops your tree targets, and saving a tree that references one its crops don't define is now rejected outright. Mango, for example, carries eleven — among them:

CodeMeaning
tree_ageAge of the trees, the usual gate between young-orchard and mature-orchard advice.
transplant_dateWhen the block was transplanted.
age_at_transplant_monthsHow old the material was at transplanting.
rootstock_typeRootstock used — drives vigour and salinity tolerance.
graft_union_height_cmHeight of the graft union.
transplant_height_cm / transplant_trunk_diameter_cmSize of the material at planting.
nursery_sourceSupplier the material came from — for tracing a problem back to a batch.

Level 3 — Key

KeyTypeMeaning
valuefollows the definitionThe recorded value. Its type comes from the attribute's own definition: a number for numeric fields, a date for dates, text for text and single-select, and a list for multi-select — which is only meaningfully compared with in, = or ≠.

9. Tree parameter params

The one source that appears on the right of a comparison rather than the left. Instead of hard-coding ≤ −1.5, a tree declares a named parameter and compares against that — so the same tree can be re-tuned per tenant without touching its logic, and the threshold gets a name that explains what it is.

  • Right-hand side only — the left is always observed data
  • Declared in the tree's own parameters block, with a default
  • Checked at save time — a reference to an undeclared parameter is rejected

Level 2 — Parameter name

Whatever the tree declares. A parameter carries a type (number, integer, boolean, string, enum), a default, and optional min/max bounds. Tenants can override the default without forking the tree.

Two things worth remembering. First, an unresolvable reference is not an error — it is a silent false, and the node takes its on miss branch. Second, the anomaly keys (baseline_deviation on the imagery and weather indices) are almost always a better threshold than raw values: they calibrate themselves to each block or farm, so one rule works across varieties, soils and seasons.
