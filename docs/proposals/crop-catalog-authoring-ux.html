AgriPulse · platform admin · design proposal

Crop catalog authoring,
without the wall of fields.

Three UX directions for the two screens that author the crop catalog — the Crop → Variety → Strain taxonomy and the typed attributes that ride on it. Every direction keeps exactly the functionality shipped today. Nothing is added, nothing is dropped. The panes below are live: click the trees, switch the types, open the sections.

What's actually wrong

The density is real, and it is concentrated in one editor

/platform/crops holds a six-field crop form, but it opens inline, and so do the variety and strain forms — three different forms can be pushed into the same tree at once, each shoving the rows below it down the page.

/platform/crops/:id/attributes is where it gets heavy. One flat two-column grid carries up to twenty controls, and roughly half of them appear or vanish depending on the chosen type:

  • Always — code, type, name EN, name AR, group code, sort order, always-required, reportable, two gate boxes.
  • Create only — variety, strain.
  • Numeric only — unit EN, unit AR, minimum, maximum, and decimal places for decimal.
  • Text only — max length.
  • Select only — the options repeater.
  • Only once a group code is typed — group name EN, group name AR.

Four specific problems fall out of that, and all three directions below attack the same four:

  • Fields reflow under you. Picking a type mid-form re-lays out the grid; controls move while you're reading them.
  • Attachment is asked twice, abstractly. Two dropdowns (variety, strain) express a position you were already standing on in the tree.
  • Presentation is typed, not seen. group_code, group_name_en, group_name_ar and sort_order are four text inputs describing a layout that is rendered live two feet to the right.
  • Gates are the hardest concept and get the least room — two identical boxes at the bottom, distinguished only by their headings.
Scope note — a large part of the crop catalog has no UI at all. Growth stages, size classes, thresholds and the GDD base temperatures are all first-class catalog data that the admin API accepts on every taxonomy level, and none of them can be reached from any screen. That is a bigger gap than the form's density, and it gets its own section below. The three directions above reproduce today's screen exactly, as briefed — so they reproduce the gap too.
ACatalog inspector

One tree, one inspector, forms that never move the page

The tree stops being a place where forms erupt and becomes a permanent left rail. Whatever you select is described in a stable right-hand inspector. The attribute editor keeps its single-form shape but is type-first and sectioned, so you only ever see the controls your chosen type actually uses.

The gap you spotted

Growth stages are catalog data, and no screen can author them

You're right that stages aren't on the screen — and it isn't that the mockups dropped them. Nothing in the frontend can author them. phenology_stages is JSONB on the crop, with phenology_stages_override on the variety and the strain; the admin create and update endpoints accept all three, farms/phenology.py validates them strictly, and the auto-advance task, the recommendation engine and plan-template authoring all read them. But cropCatalog.ts doesn't type the field, so no control exists anywhere. Today a stage ladder is set outside the product.

Stages are the one that actually deserves purpose-built UX rather than another pair of inputs, because the rules are conditional in a way a generic form handles badly:

  • The available advance modes depend on the crop's cycle. A perennial may only use calendar_doy or manual; an annual may use days_from_planting, gdd_from_planting or manual. The server rejects the wrong one.
  • gdd_from_planting requires gdd_base_temp_c on the crop — a field that also has no UI. So one missing number silently makes a whole mode unusable.
  • Each mode carries different operands — day numbers, GDD sums, or MM-DD windows that may wrap across the year end.
  • Codes and orders must both be unique, and the ladder is an ordered sequence — exactly the thing a list with drag-to-order expresses and a JSON blob does not.
  • An override at variety or strain replaces the whole ladder, it does not merge. That is the single most dangerous thing about this data and it must be stated in the UI, not in a docstring.

Yes — every level can carry its own ladder, and the data model already allows it

To answer the question directly: mango.alphonso and mango.kitti can hold completely different ladders, and mango.alphonso.a1 can differ again from Alphonso. That is not a change we need to make — resolve_phenology_stages() in farms/crop_thresholds.py is exactly eight lines of deepest non-NULL wins:

  • Strain beats variety beats crop. A node with no override of its own resolves to its nearest ancestor that has one — a strain falls back to its variety, not straight to the crop.
  • Wholesale replace, never merge. An override supplies the entire array, so a variety can define five stages where the crop defines six, or rename and re-window all of them.
  • An override can be cleared. Sending phenology_stages_override: null sets the column back to NULL and the node resolves to its parent again — so "revert to inherited" is a real, supported action, not a delete-and-retype.
  • Every level is still validated against the crop. A variety override is checked against the crop's is_perennial and gdd_base_temp_c, so a variety cannot smuggle in a mode the crop's cycle forbids.

So the work is UI, not schema. The editor below is driven by the taxonomy: pick any node and you get the ladder that resolves there, plus whether it is owned or inherited and from where. Alphonso, Kitti and Clone A1 each carry their own; Sindhri and Clone A2 inherit. Wheat is annual, so its modes and axis differ.

Common to all three

Five moves I'd make regardless of which one you pick

  • Attachment comes from selection, not dropdowns. Where you are in the tree (A, C) or an explicit “attach to” with the tree visible (B) replaces the abstract variety + strain pair.
  • Type is chosen first and visibly locked afterwards. It governs half the form; asking for it in the middle of a grid is what makes the form reflow.
  • Gates read as sentences. “Show only when Irrigation method is one of Drip, Micro-sprinkler” instead of a heading, a select and a checkbox list.
  • Group is a picker, not three text fields. Choosing an existing group reuses its EN/AR names; only “New group…” asks for them.
  • Permanence is shown, not discovered. Code, type and attachment carry a lock affordance and an explanation, rather than silently going disabled.

Recommendation

A now, C later — and take B's gate step into whichever wins

A removes the two things you actually feel — the page reflowing under you and controls that don't apply to your type — for the least work, and it leaves the current editor's field set and validation intact.

C is the direction that ends the problem rather than reducing it, because it deletes four controls instead of rearranging them and makes inheritance legible. It's the right end state, and a bigger bet.

B is the weakest as a whole system — a flow is heavy for a screen a platform admin returns to — but its step 3 is the best treatment of gates here. That step belongs in A or C regardless.

On stages: the redesign is the moment to add them, and I'd put the ladder in ahead of rearranging the attribute editor. A form that is merely dense is a worse experience; catalog data with no screen at all is a capability the product doesn't have. The two are independent — the ladder can ship on today's layout if you'd rather not wait.

Tell me which direction to take forward, and whether stages come first. The rest of the unwired fields (GDD temps, thresholds, indices, scientific name, season days, attribute descriptions) are plain additions once we've agreed they belong on the screen.
