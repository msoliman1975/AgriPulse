Investor holdings

A design for farms that an investment company runs and sells in parts to investors. Part A covers the web app. Part B covers the new Android app, AgriPulse Investor.

1. The 10 decisions

#QuestionDecisionWhat it means for the build

A database exclusion constraint stops two ownership periods of one holding from overlapping:

EXCLUDE USING gist (holding_id WITH =, daterange(start_date, end_date, '[]') WITH &&)

This needs the btree_gist extension. A transfer ends the current row on day D−1 and starts the new row on day D, in one transaction.

3.5 Harvest records new tables harvest_records, harvest_allocations

TableFields
harvest_recordsblock_id, block_crop_id, season_label (text, example "2026"), harvest_date, quantity_kg, status (draft | published | corrected), notes_internal, audit fields.
harvest_allocationsharvest_record_id, holding_id, investor_id, holding_area_m2, block_area_m2, share_pct, suggested_kg, final_quantity, final_unit (kg | t), final_kg, changed_reason, confirmed_by, confirmed_at. Status draft | published | corrected.

The flow follows decision 12:

  1. Staff enter the block total in harvest_records.
  2. The web app fills suggested_kg for each holding: block total × area share. It stores both areas and the share as they were at that moment.
  3. Staff confirm each number or type a different one. A change from the suggestion needs a short reason, kept for audit.
  4. Publish sends each investor only final_quantity and final_unit, exactly as staff entered them.

Example: block 20 feddan, holding 2 feddan, share 10.00%, block harvest 200 t. The web app suggests 20 t. Staff change it to 19.5 t, because the edge rows are young trees. The investor sees "19.5 t" and nothing else.

Farm management maintains the number after publish. A correction writes a new row with status published and marks the old one corrected. The app shows the new number with a "Corrected" label and sends no push.

Note: "Season as an entity" is designed but not built. Until it is, season_label is free text. When seasons exist, a migration replaces it with a foreign key.

4. Rules the system enforces

#RuleWhere it is enforced
R1A holding lies inside its block. A tolerance of 0.5 m lets a vertex sit on the block border.Database trigger with ST_CoveredBy(holding, ST_Buffer(block::geography, 0.5)). The API also checks it, so the web app can show the error before save.
R2Holdings in one block do not overlap. Touching edges are allowed.Trigger: refuse when ST_Relate(a, b, 'T********') is true for another live holding in the block.
R3A holding is valid and simple: no self-crossing, no holes in the first release.Reuse farms/geometry.py validation.
R4A holding sits on a leaf unit only. It cannot sit on a pivot that has sectors.API check on unit_type and child units. This stops one harvest from being counted twice.
R5Area for share uses one method for both shapes: ST_Area(boundary::geography).Service code. This keeps the share correct even when a farm uses a different UTM zone.
R6A block edit that leaves a holding outside the new border is refused. The error lists the holdings.Block update service, plus the R1 trigger on the block side.
R7A block with a current owner on any holding cannot be archived or deleted.Block service.
R8A holding's boundary cannot change while it has a current owner, unless the user has holding.redraw_sold. Each redraw writes an audit row.Holding service.
R9Ownership periods of one holding do not overlap.Exclusion constraint (section 3.3).
R10An investor update or harvest record cannot be published without both Arabic and English text.API.
R11A published holding harvest number is never overwritten. To fix it, staff publish a correction (section 3.5). The history stays.Harvest service.
R12The sum of final numbers in a block may differ from the block total. The web app shows the difference to staff but does not block publish.Web app warning only.

5. Access and security

5.1 A new role: Investor

Add Investor to backend/app/shared/rbac/role_capabilities.yaml. It has one capability, investor_app.use. It has none of the existing capabilities, so every existing route refuses an investor token through requires_capability.

All investor reads go through a separate router, /api/v1/investor/…. Each query filters by the investor row linked to the caller's user id. The caller never passes an investor id.

5.2 Mobile only

  • Keycloak gets a new public client, agripulse-investor. The investor router accepts a token only when its azp claim is agripulse-investor.
  • The web app checks the role after login. For an investor, it shows one page: "This account works in the AgriPulse Investor app" with a download link. It loads no other data.
  • Staff users cannot log in to the investor app. The investor client allows only users with the Investor role.

Warning: Add the new client to agripulse-realm.json with known fields only. An unknown field in that file crashed every Keycloak pod in the past. Also note that the Scout client agripulse-mobile is missing from both realm files today.

5.3 What the investor API never returns

The investor API uses its own response schemas. Each one lists allowed fields. It never returns these:

  • Other holdings in the same block, or other investors.
  • The share %, the block total harvest, the suggested number, or the reason for a change.
  • Block health, decision tree verdicts, findings, alerts, index values, scout visits.
  • Internal notes, contract references, staff names other than the relationship manager.
  • Farm boundary or other blocks.

A test asserts the exact field set of every investor response. A new field then fails the test until someone adds it on purpose.

6.4 True-colour image

AgriPulse stores index images only (NDVI and others). It has no true-colour image. Two ways to meet decision 5:

Option 1: basemap first

Show the outline on a commercial satellite basemap. Resolution is about 0.5 m, so a 2-feddan holding is clear. The image has no date and can be 1 to 3 years old.

Work: about 2 days.

Option 2: AgriPulse true colour

Add a true-colour product (bands B04, B03, B02) to the imagery pipeline. Store one image per block per clear scene, and show its date. Resolution is 10 m, so a 2-feddan holding covers about 84 pixels and looks blurred.

Work: about 5 to 8 days.

Recommendation: ship option 1 in the first release, and add option 2 later as a "Latest image (date)" switch. Investors then get a sharp map now and a dated image later.

7.4 Push messages

The server sends data-only FCM messages, as for Scout. The app builds the visible message in the investor's language. A tap opens the holding and the matching tab. When an investor has 2 or more holdings in one block, they get one message that names all of them, not one message per holding.

7.5 Distribution

  • Now: a signed APK, downloaded from a company page. The invite email has the link.
  • Sign the APK with an upload key kept in the team's secret store. Google Play App Signing accepts this key later, so installed users can update from the store.
  • The app checks /investor/app-version at start and shows "Update required" when the APK is too old.
  • Later, Google Play: needs a privacy policy URL, a data safety form (email, name, push token), a store listing in Arabic and English, and a test account for review.
  • Add an APK build job to CI. Scout has none today, so every Scout APK is built by hand.

9. Risks and open questions

9.1 Risks

  • Manual numbers can drift from the suggestion. Staff can change any harvest number (decision 12). The reason field and the audit row are the only record of why. A monthly report of changed numbers helps managers review them.
  • Block redraws. When staff redraw a block, every suggested number in it changes for future harvests. Rule R6 stops a redraw that cuts a holding, but a larger block lowers every share. The web app must warn: "This changes the share of 9 holdings".
  • Data leaks to investors. The investor API is the only gate. The field-set test in section 5.3 is the main guard.
  • Health data at the edges. Decision 5 hides health. The true-colour image still shows bare or yellow patches. Staff should expect questions about them.
  • Two apps, one Firebase project. Scout and Investor tokens must stay apart, or an investor could get a scout's visit message. The app column on device_tokens handles this.

9.2 Open questions

None. Decisions 11 to 17 in section 1 answered the 7 earlier open questions.
