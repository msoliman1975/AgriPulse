01

The platform was pre-wired for this, then left unbuilt

Both ends of the scouting loop already exist in code. Only the middle is missing — and one capability was declared, granted to six roles, and never implemented.

An honest correction, carried forward

An early draft of this work claimed the loop was already closed. The mechanism is live — recommendations/service.py:296 loads a per-block signals snapshot into ConditionContext. The content is not: across all 18 seed trees only four signal codes appear (soil_salinity, petiole_no3n, petiole_p, petiole_k), every one a lab value. No tree reads a scouting observation. Closing the loop is scope (§06, §12), not a freebie.

The tell: a stub capability

scouting.record is declared in shared/rbac/capabilities.yaml:378 — "Log a scouting observation (notes, photos)" — with scope: farm, status: stub, granted to six roles, and implemented by zero endpoints. It is a reserved contract waiting for this module.

expired is a flag, not a closure

The sweep marks it, escalates to the supervisor, and the visit stays actionable. Auto-closing overdue work would make a neglected farm look identical to a healthy one.

"I couldn't tell" is a real answer

Forcing every visit into resolved/unresolved manufactures false data. inconclusive routes the block back to an agronomist instead of pretending it was handled.

The index that stops a daily flood

Partial UNIQUE on (recommendation_id) WHERE recommendation_id IS NOT NULL AND status NOT IN ('cancelled','expired'). The evaluator re-walks every tree daily — without this, a persistent NDVI dip queues a brand-new visit every single morning.

scouting_routing_rules

Resolved most-specific-first: block → farm → tenant. Carries mode (triage | auto), default_assignee, fallback_assignee, min_severity, template_id, default_due_hours.

auto with no resolvable assignee degrades to triage

It never drops the visit. Silent loss is the worst outcome available here.

device_tokens

user_id, token (UNIQUE), platform, app_version, locale, last_seen_at, revoked_at. Multi-device per user is expected; a reaper revokes tokens unseen 90 days or rejected by FCM.

Observations — per row, not per visit

The submit call is one batch, but location and time are recorded per observation row. signal_observations already carries location_point, location_mode, time and attachment_s3_key on every row, and the ST_Within trigger is FOR EACH ROW.

{ "idempotency_key": "0198f3…",
  "outcome": "inconclusive",
  "visit_location": { …fix at submit — the default rows inherit… },
  "observations": [
    { "definition_code": "canopy_vigour", "value_categorical": "poor" },
    // each photo is its own row: its own shutter time and its own fix
    { "definition_code": "scout_photo", "attachment_s3_key": "…/a1.jpg",
      "observed_at": "2026-08-08T07:31:12Z",
      "location": { "mode": "point_in_entity", "lat": 29.97661, "lon": 32.52288,
                     "accuracy_m": 6.0, "source": "gps_at_capture" } },
    { "definition_code": "scout_photo", "attachment_s3_key": "…/a2.jpg",
      "location": { "mode": "free_point", /* 14 m outside — keep the real reading */ … } }
  ] }

A scout photographs a lesion at the north edge, walks back, and fills the form four minutes later thirty metres away. Stamping every row with the submit-time fix puts the evidence in the wrong place — and the photo's coordinate is the only thing that makes it re-findable next visit.

The GPS fallback ladder

Prefer free_point; entity is the lossy one

The CHECK forces location_point to NULL under entity, discarding the reading. free_point keeps the coordinate and block attribution and only skips the containment check. And never block submission on GPS — losing an observation is far worse than losing its point.

06

The signals platform tier new tier

The S0 blocker: no forms, no app. And there is nowhere today to publish a curated scouting form set once, for everybody.

The problem, precisely

SignalDefinition, SignalTemplate and SignalTemplateDefinition live in tenant_<id>.* and are authored per tenant at /config/signals/:farmId. There is no public.signal_definitions and no platform catalogue. Unlike decision_trees and crops, signals have no platform tier at all — so an improvement to a scouting form can never reach anyone but the tenant who made it.

CataloguePlatform tier?Authored by
decision_treesyes — nullable tenant_idYAML seeds → sync_from_disk at API startup
crops, plan_templatesyesPlatform UI (/platform/crops, /platform/plan-templates)
signal_definitionsnoneTenant only

Design — mirror decision_trees, author like plan_templates

Move the three definition/template tables to public with a nullable tenant_id: NULL = platform-curated, non-NULL = tenant-authored. Observations and assignments — which are per-farm operational data — stay in the tenant schema.

BEFORE                              AFTER
tenant_x.signal_definitions         public.signal_definitions   tenant_id NULL = platform
tenant_x.signal_templates           public.signal_templates     tenant_id NULL = platform
tenant_x.signal_template_defs       public.signal_template_definitions
tenant_x.signal_assignments   ───►  tenant_x.signal_assignments (unchanged, per-farm)
tenant_x.signal_observations  ───►  tenant_x.signal_observations (unchanged, hypertable)

read:  WHERE tenant_id IS NULL OR tenant_id = :tid   ← the pattern, written twice already

What makes this feasible

  • signal_observations.signal_definition_id has no FK — it is already a logical reference, so the hypertable is untouched.
  • Tenant → public FKs are legal and already used (TenantMembership.user_id → public.users.id), so signal_assignments.signal_definition_id can point at public.signal_definitions.id.
  • Code uniqueness partitioned per scope is exactly what decision_trees migration 0024 already does with partial unique indexes.

What has to change

#ChangeRisk
T1New public.signal_definitions / _templates / _template_definitions with nullable tenant_id + partial unique on code per scopelow
T2Per-tenant data migration: copy each tenant's rows up, stamping tenant_id, preserving ids so assignments/observations keep resolvinghigh — runs per schema; must be idempotent and reversible
T3Repoint the two real FKs (signal_assignments, signal_template_definitions) at the public tablesmedium
T4snapshot.py raw SQL joins public.signal_definitions with the two-tier predicatemedium — it is the engine's read path
T5Repository/service/router resolve both tiers; tenants may not edit platform rowslow
T6/platform/signals catalogue UI + seed the scouting forms (§ below)low
T7Update the purge manifesthigh if missed

T7 will fail CI if forgotten, and T2 is the one to rehearse

Tenant purge enforces "no orphans" — tables leaving the tenant schema change what purge must delete, and a stale manifest fails the guard. And T2 preserves primary keys across a schema move while a live hypertable references them logically: rehearse it against the 36-block Bashayer clone before it goes anywhere near prod.

Author in a UI, not YAML — deliberately unlike trees

Trees are YAML because they carry evidence blocks with DOIs, citations and transferability ratings — scientific claims that deserve diffs and code review. Signal definitions carry no such provenance; they are vocabulary. So platform signals are authored at /platform/signals like crops and plan templates, seeded once by a data migration. This avoids the UI-versus-seeder conflict entirely — there is no sync_from_disk to overwrite an edit on the next deploy.

Identity, authentication and access

The hardest constraint in the whole project: these workers do not have email addresses, and the identity core requires one.

Three layers that already exist

LayerTableCarriesLogin?
Userpublic.userskeycloak_subject, email, phonethe login
Memberpublic.tenant_memberships + farm_scopestenant, farms, roleauthorises
Workertenant_x.resources kind='worker'role, phone, assignableno

Every mobile user is all three, joined by resources.membership_id (U-3, live since June, unused until now). A worker row without membership_id is unlinked labour: schedulable, but cannot log in or be pushed to. That is correct — not every field hand needs an account.

The blocker

public.users.email is CITEXT NOT NULL with uq_users_email (0003_iam_tables.py:74), and KeycloakAdminClient sets "username": email, "email": email. A worker with no email cannot be provisioned today.

D7 — phone as the username, email synthesized

public.users
  phone         = +201001234567                            ← real, the identity
  email         = +201001234567@scouts.agripulse.cloud     ← synthetic: satisfies NOT NULL + UNIQUE
Keycloak
  username      = +201001234567
  emailVerified = false
  credential    = 6-digit PIN, temporary = false
  1. Normalise to E.164 on write. Supervisors type 01001234567; store +201001234567, or the same person gets two accounts.
  2. Never synthesize onto .local — Keycloak 26 strips those. Use a domain we own, with no MX record, so nothing can ever be delivered.
  3. notification_channels must default to ['in_app','push'] — the system default ['in_app','email'] would fire mail at a fake address forever.
  4. The username stays the phone permanently. If a scout later gains a real email, update users.email and leave the username alone.
  5. Flag synthetic addresses so the Team screen and reporting can hide them.

The existing SMTP fallback is the wrong shape

_issue_credential already tolerates dead SMTP via _set_temporary_password — but that sets temporary: true, forcing a Keycloak browser UPDATE_PASSWORD form, which is precisely what this persona cannot complete. Enrolment needs a temporary:false sibling.

Keycloak client and session

  • New public client agripulse-mobile: Authorization Code + PKCE in an Android Custom Tab — never an embedded WebView.
  • Redirect agripulse://auth/callback; the same scheme carries push deep links.
  • offline_access scope for the ~90-day field session. Do not stretch realm SSO lifetimes — that would weaken the web app for everyone.
  • Refresh token in @capacitor/preferences, backed by Android Keystore.
  • farm_scopes mapper unchanged — the middleware already parses JSON-string items.

Offboarding — five layers, and one is always forgotten

  1. Revoke farm_scopes → set_farm_scopes() syncs Keycloak.
  2. Membership → inactive.
  3. resources.archived_at — history preserved.
  4. Revoke device_tokens, or a deregistered phone keeps buzzing.
  5. Revoke the Keycloak offline token.

Step 5

An offline_access token outlives an access-token TTL by design; scope revocation alone does not kill it. Until step 5 runs, "we removed their access" is false — for up to 90 days.

FieldWorker cannot use the app at all

U-2 added it to the resources.role vocabulary as worker-only with zero capabilities. Anyone recorded as FieldWorker must be re-roled to Scout before they can be given an account. Audit the worker table before the pilot — it is free, and it tells you how many accounts you actually need.

Recycled phone numbers

Egyptian numbers get reassigned. With username = phone, never bolt SMS-based password reset onto this model without re-verification, and make offboarding archive the user, not just the membership.

Push pipeline

  • push joins _PER_USER_CHANNELS and _KNOWN_CHANNELS in notifications/subscribers.py; per-user opt-in already exists.
  • New sender notifications/push.py beside smtp.py / webhook.py.
  • Templates keyed (template_code, locale, channel='push', version) — one per origin, EN + AR.
  • Data message, not notification-only, so the app controls presentation and cold-start deep links.
  • Add visit_id to notification_dispatches for the existing idempotency index.

Push is never the source of truth

FCM delivery is best-effort and fails silently on some OEM builds. The visit list reconciles on every app open. A dropped push must never mean lost work.

On /platform/decision-trees

There is no platform decision-tree page and there never was one. Global trees (tenant_id IS NULL) are authored only as YAML and upserted by sync_from_disk() at API startup — deploying the API is what publishes a tree. Tenants can already see them. What is missing is a place to manage the global catalogue. Recommendation: a read-only catalogue (C1). Do not make the DB the source of truth while the seeder still runs — the UI writes a row, the next deploy overwrites it.
