What changed

Requirement A — the current assignment, its crop fields and its from → to are all on screen while you assign, so you can see what you are about to replace.

Requirement B — Show history is off by default: one card, no clutter. On, you get every assignment with its range, plus a timeline that makes gaps and adjacency obvious at a glance.

Today is_current is a stored boolean, flipped only when someone assigns a new crop. A potato assignment that finished in March still reads as current in August. Deriving it from the range fixes that without a data migration of its own.

Overlap is rejected

One crop at a time per block, enforced by an exclusion constraint — not by application code that a bulk import could bypass.

Potato · Spunta cannot start 2026-01-15: block AG-R05-B02 is under Tomato until 2026-03-10.
Fix: end tomato on 2026-01-14, or start potato on 2026-03-11.

Gaps are allowed, and shown

A fallow block is legitimate. It is not an error — but it should be visible rather than inferred from two dates that don't touch.

Pattern 1 · Valid time, not a flag

Add effective_from (NOT NULL) and effective_to (NULL = ongoing) to block_crops. Derive “current” as effective_from <= today AND (effective_to IS NULL OR effective_to > today).

This is the pattern grid_configs already uses (tenant 0054) and the reason its docstring gives: “when did we change this” and “what period does it describe” are different questions. block_crops currently conflates them in is_current, which is why a finished crop still reads as current.

Pattern 2 · The database owns non-overlap

An EXCLUDE USING gist constraint over (block_id WITH =, daterange(effective_from, effective_to) WITH &&).

Service-layer checks are bypassed by bulk import, backfills and any future writer. The bulk AOI upload and the grid rezone both already write assignments-adjacent data. A constraint cannot be forgotten; it needs the btree_gist extension, which the migration adds.

Pattern 3 · Closing is a consequence, not a chore

Assigning a crop sets the previous assignment's effective_to to the new effective_from in the same transaction, and says so before you commit.

Two-step “end then assign” is where gaps and overlaps come from. Showing the consequence inline — “this ends Tomato on 10 Mar 2026” — keeps the automatic behaviour from being a surprise, which is the same reason the crop-fields form warns before a gate clears a value.

Pattern 4 · History is a disclosure, not a page

One checkbox on the same panel. Off → the current card only. On → timeline + table, in place.

A separate history screen loses the comparison that makes history useful: what is on the block now versus what was. The checkbox state is worth persisting per user, not per block.

Migration sketch

-- tenant migration
ALTER TABLE block_crops
  ADD effective_from date,
  ADD effective_to   date;

-- backfill: never lose a row
-- from := planting_date, else created_at
-- to   := next assignment's from,
--         else actual_harvest_date,
--         else NULL when is_current

CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE block_crops ADD CONSTRAINT
  ex_block_crops_no_overlap EXCLUDE USING gist (
    block_id WITH =,
    daterange(effective_from, effective_to) WITH &&
  ) WHERE (deleted_at IS NULL);
The backfill is the risky half, not the columns. Real data may already contain two rows that overlap under any rule we pick — the constraint would then refuse to be created. The migration must report those blocks rather than guess.

Open questions

  • season_label is NOT NULL today. With real dates it is derivable — keep, make optional, or auto-fill from the year?
  • Does effective_to exclude its end date (half-open [from, to))? The exclusion constraint assumes so; the UI should say “until” rather than “to”.
  • Should ending an assignment be blocked while its season plan is still open?
