Users, Members & Workers
— three people-models, one platform

Three concepts in the app all describe "a person connected to a farm" — but they live in different tables, carry different role vocabularies, and never link to each other. This document maps how each works today, where they overlap, and a staged plan to unify them.

01The short version

If you read nothing else.

Five things to know

  • User vs Member is intentional and healthy. A User is one global login identity (Keycloak-backed, one row per email). A Member is that user inside one tenant — a tenant_membership row with its own status and roles. Same person, two layers. This is correct multi-tenant design; keep it.
  • "Workers" is a different beast entirely. A Worker is a resources record (kind='worker') — a name + role + phone with no login and no permissions. It exists only to be tagged onto plan activities. It is not in the IAM stack at all.
  • The real problem is duplicated role vocabularies. Farm IAM roles (Agronomist Scout FieldOperator FarmManager) and Worker roles (agronomist scout operator manager) are the same words in two unlinked tables. The same human can exist as both, twice, with no connection.
  • A third assignment path exists too: farm.farm_manager_id and block.agronomist_id point directly at user IDs — a domain-routing shortcut that bypasses both IAM roles and the worker catalog.
  • "Workers" also means Celery (the backend/workers/ infra). Pure name collision — never user-facing — but it muddies conversation and search. Worth a rename.
🎯

The opportunity in one line: unify the role vocabulary across IAM farm-scopes and the worker catalog, give a worker an optional link to a login member, and collapse the ad-hoc *_id domain fields into that one model — so "who is the scout on this farm" has exactly one answer.

User → Member is not the overlap to fix. It's a clean two-layer split: identity (global) vs membership (tenant-scoped), which is exactly what lets one consultant belong to several tenants. The confusion is purely naming — both the screen and the route are called "Users" even though they manage memberships. A label tweak, not a refactor.

03The role landscape — five planes

"Role" is overloaded. There are four IAM role planes (permission-bearing, capability-checked) plus a fifth descriptive plane on workers that grants nothing. Access checks never compare role strings — they resolve capabilities through Platform → Tenant → Farm.

Platformon the User · global
PlatformAdmin PlatformSupport → platform_role_assignments
Tenanton the Member · tenant-wide
TenantOwner TenantAdmin BillingAdmin → tenant_role_assignments
Farm scopeon the Member · per farm
FarmManager Agronomist FieldOperator Scout Viewer → farm_scopes
Worker labelon the Resource · grants nothing
agronomist operator scout field_worker manager → resources.role
Domain pointerson farm/block · direct user_id
farm.farm_manager_id block.agronomist_id → columns on domain tables
⚖️

Only planes 1–3 are real permissions. Resolution is first-match in order Platform → Tenant → Farm, all via has_capability(...) against the YAML capability maps — code never branches on a role name. Plane 4 (worker label) is purely cosmetic. Plane 5 (the *_id pointers) is domain routing that no capability check consults — a fourth, redundant way to say "this person owns this farm/block."

Why this hurts

The duplicate-person trap

# Today, Salma the agronomist is…
member → farm_scope Agronomist
…and ALSO, separately…
worker → role agronomist

# two rows, no link.
# Assign activity? pick the worker.
# Check permission? read the scope.
# Nothing ties them together.

Consequences

  • Double data entry — invite Salma and re-create her as a worker.
  • Drift — she leaves; her membership is suspended but the worker record lingers on activities.
  • No accountability join — "show every activity Salma logged" can't be answered from her login identity.
  • Vocabulary skew — FieldOperator vs operator, FarmManager vs manager means reporting must hand-map.
  • Three answers to one question — "who manages this farm?" → a farm_scope, a worker, or a farm_manager_id.
⚠

Edge already in the codebase: the invite endpoint defaults tenant_role="Viewer", but Viewer is a farm-scope role, not a tenant role. That single mislabel is exactly the class of bug this fragmentation breeds — and it's the same family as the production "Viewer invites 500'd" incident already fixed in migration 0036.

06Unification plan — staged & low-risk

Ordered so each step ships value alone and nothing forces a big-bang migration. Impact/effort are rough engineering calls.

✅

Status (2026-06-14): U-1, U-5, U-2, U-3 implemented in the working tree (uncommitted). U-1 relabels the tenant screen "Team" (not "Members" — that name is already the per-farm farm-scope page). U-2 canonicalises worker roles to the FarmRole vocabulary (tenant migration 0043 + alignment test). U-3 adds the optional membership_id link (tenant migration 0044, link picker in Settings ▸ Workers). Verified: frontend tsc + eslint + prettier, backend ruff + mypy + unit test, linear migration chain. U-4 deferred to the farm-block-config work that already touches farm_manager_id/agronomist_id. The deeper unified activity picker (workers + members in one board control) is incremental follow-up.

U-1

Rename the screen: "Users" → "Members" (or "Team")

impact · med effort · low

What: The /v1/users management UI manages tenant memberships, not global users. Relabel it (i18n + nav) to "Members" / "Team," and reserve "User" for the global identity / profile. No schema change.

Why: Removes the single biggest source of conceptual confusion at near-zero cost. Makes the User-vs-Member layering legible instead of hidden.

U-2

One shared role vocabulary

impact · high effort · med

What: Make worker labels reuse the farm-role enum. Map operator→FieldOperator, manager→FarmManager, align casing, and keep field_worker (generic labour) + Viewer as the only plane-specific extras. Define it once (the existing role enum / capability YAML) and have both the worker catalog and farm-scopes read from it.

  • Reporting and pickers stop needing a hand-maintained translation table.
  • A backfill maps existing resources.role strings to the canonical set.
  • Pure value normalization — no relationship change yet, so it's safe to ship first.
U-3

Let a Worker optionally be a Member

impact · high effort · med

What: Add a nullable membership_id on the worker resource. A worker is then one of two flavours: linked (a real login member who also does field work) or unlinked (a labourer with no account — the common case). The activity-assignment UI shows both in one picker.

  • Invite Salma once → she's available as a worker automatically, no re-entry.
  • "Every activity Salma logged" becomes a join, not a guess.
  • Unlinked workers still work exactly as today — nothing breaks.
  • Suspending a member can flag/auto-archive their linked worker record.
U-4

Retire the ad-hoc *_id pointers

impact · med effort · high

What: Treat farm.farm_manager_id and block.agronomist_id as derived from the unified model (the member holding the FarmManager scope on that farm; the linked agronomist on that block) rather than free-standing columns. Migrate readers to the resolver, then drop the columns once nothing writes them.

Why: Collapses the fifth role plane into the canonical one so "who manages this farm" has exactly one source of truth. Highest effort because callers and the farm-block-config model touch these fields — do it last.

U-5

Rename Celery "workers" in code & docs

impact · low effort · low

What: Standardize on "task workers / queues" for the Celery tier in code comments, runbooks and Helm component labels. Leave the people-facing "Workers" UI as-is. Eliminates the search/onboarding ambiguity without touching deployments.

07Target model — one person, clearly layered

After U-1…U-4, the same human resolves through a single chain instead of three parallel ones.

Today — fragmented

User (login)
 └ Member (tenant)
    └ farm_scope Agronomist

Worker agronomist ⟂ no link

block.agronomist_id user_id ⟂ no link

Target — one spine

User (login, global)
 └ Member (tenant)
    ├ farm_scope Agronomist ← permission
    └ Worker (linked) → activities

Unlinked Worker (labour, no login) → activities

"agronomist of block" = resolver, not a column
