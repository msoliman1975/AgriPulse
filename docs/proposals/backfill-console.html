How the three capabilities fit together

There are three things here: start a backfill, compute indices, and watch what's running. The screen above stacks all three, which is the simplest thing that works but makes the page long and buries the run history in the middle. Three ways to arrange them:

Option 1

One screen, stacked

New backfill
Runs
Compute indices

For: nothing hidden, no navigation, one page to learn. What the mockup shows today.

Against: long scroll. Runs — the thing you return to most — sits between two forms you use rarely. Gets worse as the table grows.

Option 2

One item, three tabs

BackfillIndicesRuns
Active tab

For: each capability gets a clean, full-width surface. Familiar pattern, cheap to build.

Against: you submit on one tab and the result appears on another — the tab switch after every run gets old fast. Status is invisible unless you go looking.

Option 3 · recommended

Runs is the screen

+ Backfill+ Indices
Runs
Drawer

For: matches what the screen is actually for — you check status far more often than you start a job. Both actions open a drawer over the list, so you submit and watch the row appear behind it. One unified history.

Against: a drawer holds less comfortably than a full page, and the estimate rail needs to fit inside it.

I'd take Option 3. The deciding argument is that both actions write into the same run table — splitting them across tabs or pages fragments one operational history for no gain, whereas the job-console shape (list as home, creation as a transient task) is the pattern every ops tool converges on for exactly this reason. Option 2 is the safe fallback if you'd rather not build a drawer.

Why it's shaped this way

Tenant first

A platform admin has no farm context — the nav is persona-separated and there is no farm switcher. So tenant is the first field, and farm cascades from it. This mirrors the existing tenant drill-down in Health.

Cost before commit

The estimate rail is the anchor of the composer, not a footnote. A year across 35 subscriptions is real money on the CDSE free tier, and it is the one mistake here that cannot be undone by re-running.

Indices stay separate

Backfill is always raw-only — there is no inline "compute as you go". Load raw once, then reproject as often as you like without touching the provider. Imagery and weather indices are independent checkboxes, because they are separate tasks with completely different costs.

Partial is a real state

Backfills routinely half-succeed — cloud skips, provider timeouts, quota exhaustion. With no cancel, Partial carries the weight: it is a first-class status whose retry re-runs only the failed window, safe because both tasks are idempotent.

API surface

POST
/v1/admin/tenants/{tenantId}/backfill-runs
Create a run: farm, window, sources: ["imagery","weather"]. Returns the run id, or 409 if that farm is already running.
POST
/v1/admin/tenants/{tenantId}/backfill-runs:estimate
Dry run. Returns block/subscription counts, scene and unit estimates, quota headroom. No side effects.
GET
/v1/admin/backfill-runs?status=running
Cross-tenant list for the table. Polled while any run is active.
GET
/v1/admin/tenants/{tenantId}/backfill-runs/{id}
One run with its per-task detail rows — the expanded view.
POST
/v1/admin/tenants/{tenantId}/backfill-runs/{id}:retry
Re-queue only the failed slice of a partial run. Rejected if the farm has a run in progress.
POST
/v1/admin/tenants/{tenantId}/index-runs
Compute indices over stored data. Body takes sources: ["imagery","weather"]. Writes to the same run table.

What this needs that doesn't exist yet

  • A backfill_runs table. Both tasks are declared ignore_result=True, so Celery persists nothing and there is no status to read today. This table is the actual new work — the UI is a view onto it. It mirrors the existing imagery_ingestion_jobs shape: status, started_at, completed_at, counters, error.
  • Progress reporting from inside the tasks. They currently return a dict at the end. They need to write counters as they go, or the bar only ever reads 0% then 100%.
  • A quota reading. The estimate is honest only if CDSE consumption is actually tracked. Without it the panel should show scene counts and say units are unknown, rather than invent a number.
  • A capability. Something like platform.run_backfill, gated the same way the nav already gates on platform.manage_tenants.

Decisions

  • No stop or cancel. Runs go to completion. This removes the awkward part — mid-flight Celery revocation — and costs little, because a run that goes wrong is recoverable by fixing the cause and re-running: both tasks are idempotent, so a repeat only fills gaps.
  • One farm per run. Matches the existing task signature exactly, keeps progress a single honest number, and avoids a fan-out model the UI would struggle to represent.
  • Concurrency is blocked, not queued. A farm with a run in progress cannot be selected, and the API rejects a second run for the same farm. Idempotency makes a concurrent run safe but not free — it would burn processing units re-fetching scenes the first run is already pulling.
  • Platform admins only. No tenant-admin path. That stays closed until per-tenant quota accounting exists, since without it one tenant could exhaust the shared CDSE allowance for everyone.
