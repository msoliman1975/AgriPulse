Part D · Mockups · Android first

Every scouting visit is a clock already running.

The decision tree that sends a scout out also says how long they have — within_hours: 24 for a severe NDVI drop, 72 for a moderate one. That countdown is the one thing on every screen, because it is the only thing that decides what to do next.

Push · Arabic — same visit, mirrored

Data message, not notification-only

The app draws the notification itself so claim works from the lock screen and a cold-start deep link lands on the right visit.

Locale comes from the user, not the device

Templates are keyed (code, locale, channel, version), so the body is rendered server-side from user_preferences.

Push is never the source of truth

Delivery fails silently on some Android builds. The visit list reconciles on every app open — a dropped push must never mean lost work.

The 24h is not copy

It is parameters.within_hours off the tree leaf, carried into due_by.

Sorted by deadline, not by severity

A warning due in two hours outranks a critical due tomorrow. The ring makes that legible without reading a word.

Claimable is a separate section

Under mode='auto' a visit arrives already assigned. Under triage the supervisor assigns it. Unclaimed work sits in its own bucket so nobody assumes someone else took it.

Overdue never disappears

expired is a flag, not a closure. It stays at the top and escalates to the supervisor — otherwise a neglected farm looks exactly like a healthy one.

Distance is measured, so it is mono

Every number the field produced — metres, σ, hours, coordinates — is set in mono. Every sentence a person wrote is set in sans.

Human reason — instruction, author, dropped pin

Sand means a person wrote this

The only warm surface in the app. It appears when, and only when, a human typed the instruction — so the scout knows there is someone to answer to, not a threshold.

The chart is the argument

The tree branched on baseline_deviation < −1.5. Drawing the band and the line leaving it explains the decision faster than the sentence does.

Decline needs a reason

It returns the visit to the queue and notifies the supervisor. Refusing work is legitimate; refusing it silently is not.

Self-contained payload

Reason text, thresholds, block geometry and the full form definition all arrive with the visit — one fetch, and the screen is renderable from cache when the queue lands in v2.

Dark because of the sun

Map and capture run dark. Outdoors at midday a white screen is a mirror.

Cell-level, not just block-level

Recommendations already carry cell_id. Sending someone to a 40-hectare block when the anomaly is in one grid cell wastes the visit.

Bearing beats turn-by-turn

There are no roads inside a block. Distance plus a heading is what actually helps; hand off to Google Maps only for the drive.

The edge case that loses work — resolved before submit

This screen exists because the database will refuse

location_mode='point_in_entity' is enforced by an ST_Within trigger. Without this, a scout walks the block, shoots photos, taps submit — and the write is rejected by a boundary they were standing on.

Keep the real reading, don't discard it

free_point keeps the coordinate and the block attribution and skips only the containment check. entity is the lossy option — its CHECK forces the point to NULL — so it is the last resort, not the fallback.

Snapping can invent precision

Offer the snap only when the offset is within tolerance and larger than the reported accuracy. Snapping a ±30 m fix that sits 8 m out is fabricating a position.

Categorical, not numeric

Chips survive gloves, glare and hurry — and a decision tree can branch on them. A free-text field can do neither.

Photos are gated per definition

The camera only appears where attachment_allowed is set. Miss it while authoring the template and the feature silently never shows up.

Voice input is not a nicety

Arabic dictation is the difference between a note and no note for much of this workforce.

"I couldn't tell" is a real answer

Forcing every visit into resolved / unresolved produces false data. inconclusive routes the block back to an agronomist instead of pretending it was handled.

One call, one transaction

All observations post as a single batch with a client-generated idempotency key, sharing a template_observation_id. Double-tap is safe.

What "closes the loop" honestly means

Today no decision tree reads a scouting signal — the four codes trees consume are all lab values. Until the trees in §8 of the spec are authored, this confirmation is read by people, not by the engine.

Ad-hoc dispatch — Farm Console map, scouting.dispatch

The only origin carrying human words

Every other visit renders text from a template. This one carries instruction and a pin_point — which is why it gets its own surface treatment on the phone.

Reuses the console the map already is

Dispatch is an action on the existing /labs/map Farm Console, not a new page. The supervisor is already looking at the imagery when the hunch forms.

Assign is optional

Leave it empty and the visit lands in the triage queue as claimable.

Two dispatch modes, one board

Farms set mode per routing rule. auto assigns and pushes immediately; triage parks it here. The board shows both, so nothing is invisible.

Auto with no assignee degrades to triage

If the default scout is inactive and there is no fallback, the visit lands in this queue rather than vanishing. Silent loss is the worst outcome available.

One live visit per recommendation

The daily evaluator re-walks every tree. A partial unique index on recommendation_id is what stops a persistent NDVI dip from queueing a new visit every morning.

What these screens commit us to

Already exists

  • The trigger. scout_for_stress_v1 emits severity, priority and within_hours, bilingual.
  • The observation model. Typed values, photos, GPS, notes — no schema change.
  • The form model. Signal templates with ordering and required flags.
  • The role. Scout, farm-scoped, working since PR #269.

Has to be built

  • scouting_visits — dispatch, deadline, state machine.
  • A push channel plus a device-token registry.
  • Routing rules — triage and auto, resolved block → farm → tenant.
  • The scouting forms themselves. No signal catalogue exists today.
  • The Android client. The long pole.

Decide before building

  • Does v1 include the loop-closing trees? Without them, findings are read by people, not by the engine.
  • Is online-only survivable at the pilot farm? Check coverage on the actual blocks first.
  • Who provisions scouts? Every scout needs a Keycloak account.
  • SMS fallback for critical? Push alone is not guaranteed on all Android builds.
