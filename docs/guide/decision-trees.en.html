1. What a decision tree does

A decision tree is a declarative, versioned agronomic rule. It looks at everything the platform currently knows about one block, walks a branching set of yes/no questions, and lands on exactly one leaf. That leaf either produces a recommendation (or an alert), or it explicitly produces nothing.

Trees are the only thing in the platform that turns measurements into advice. Everything upstream — satellite index computation, weather ingestion, custom field signals, phenology tracking, grid anomaly detection — exists to populate the facts a tree reads. Everything downstream — the recommendations page, notifications, the plan board, the block dock's Conditions tab — renders what a tree produced.

Two kinds of output

KindMeaningConfidence
recommendation Advice a human should consider and act on. Carries a state machine (open → applied / dismissed / deferred / expired) and can be scheduled onto the plan board. Author-set, 0–1, default 0.5
alert A condition that has been detected, not a judgement call. Trees own alerts since the Stage-1 rules engine was retired. Always forced to 1 — alerts express certainty, not probability

The design stance that shapes everything

The evaluator is pure and point-in-time. It has no notion of time, history, or "has been falling for three weeks". This is deliberate: every temporal idea is precomputed into a fact before evaluation, so the rule language stays a handful of comparison operators instead of growing a query language.

That is why a rate of change is exposed as a plain readable field (slope, delta, trend_direction) rather than as a has_been_falling_for operator, and why growth stage is a resolved string on the block rather than a date calculation inside a rule. Model new temporal or derived ideas as data, not as operators.

3. How it runs

Trees are not evaluated when someone opens a page. A background sweep runs on a schedule and writes recommendations into the tenant's schema; the UI only ever reads what the sweep already produced.

Celery Beat  ──▶  recommendations.evaluate_sweep      (default: every 3600 s)
                        │
                        ├─▶ for each active tenant → evaluate_for_tenant
                        │         │
                        │         └─▶ for each block:
                        │                 1. load every active tree visible to the tenant
                        │                 2. filter by targeting  (crop / country / soil)
                        │                 3. build one ConditionContext for the block
                        │                 4. walk each tree from its root
                        │                 5. write an open recommendation per firing leaf
                        │
                        └─▶ cell-scoped trees run once per grid cell, with that
                            cell's own index means swapped into the context

Step 1 — Which trees are considered

A tree must be active and visible to the tenant. Platform seed trees (shipped in the repo) are visible to everyone; a tenant-authored tree is visible only to that tenant.

Step 2 — Targeting

Three independent axes decide whether a tree applies to a given block. A tree matches only if every axis passes (AND across axes); within one axis, any listed value is enough (OR within an axis). An empty axis matches anything.

AxisYAML keyMatched againstRule
Cropcrop_pathsThe block's crop path, e.g. mango.alphonso.short Prefix match — mango matches every mango variety and strain
Countrycountry_codesThe parent farm's country Exact, ISO 3166-1 alpha-2, normalized to upper case
Soilsoil_texturesThe block's soil_texture Exact, from the closed vocabulary: sandy, sandy_loam, loam, clay_loam, clay, silty_loam, silty_clay
Coverage guardrail

If an axis is constrained and the block's value for it is unknown, the tree does not match. A tree filtered to country_codes: [EG] will never fire on a farm whose country was never set. This is intentional — it fails quiet rather than firing on a guess — but it means adding a targeting axis to an existing tree can silently shrink its coverage. Check :candidate-blocks after changing targeting.

Step 3 — The context

One ConditionContext is assembled per block per pass: the latest index aggregates plus their trend features, the weather snapshot, farm-level weather indices, per-block disease/pest risk, the latest value of every applicable custom signal, grid anomaly verdicts, block attributes, and the tree's resolved parameters. Every source is loaded once and shared across all trees for that block.

Step 4 — The walk

Evaluation starts at root. At each decision node the node's condition is evaluated to a single boolean, and the walk follows on_match or on_miss. It ends when it reaches a node carrying an outcome. The walk is capped at 64 steps; exceeding that is reported as a probable cycle.

Every step is recorded — node id, which way it went, and the resolved value of every reference it read. That trace is what the block dock's Conditions tab and the :explain endpoint render, and it is stored on the recommendation as its evaluation snapshot.

Step 5 — Writing the result

A leaf whose action_type is no_action produces nothing. Any other leaf opens a recommendation.

Idempotency

Writes are protected by a partial unique index on (block_id, tree_id) WHERE state = 'open'. A tree that keeps matching every hour does not pile up duplicates — there is at most one open recommendation per tree per block. A new one can only appear after the existing one is resolved, dismissed, deferred or expired.

4. How it is stored

Trees live in the public schema — they are a shared catalog — while their output lives in each tenant's own schema.

Platform catalog — public

TableHolds
public.decision_trees One row per tree: code, tenant_id (NULL = platform-shipped, non-null = tenant-authored), bilingual names and descriptions, the targeting axes (crop_id / crop_path / crop_paths / country_codes / soil_textures), scope, is_active, and current_version_id.
public.decision_tree_versions One row per version: the version integer, tree_yaml (round-trippable source), tree_compiled (the JSONB the engine actually walks), compiled_hash (SHA-256, which is what makes the disk sync idempotent), and published_at / published_by — NULL meaning still a draft.

Uniqueness is partial: (code) WHERE tenant_id IS NULL for platform trees, and (tenant_id, code) WHERE tenant_id IS NOT NULL for tenant-authored ones — so a tenant can use a code that already exists in the platform set without colliding with it.

Tenant state — tenant_<id>

TableHolds
recommendations The output: block_id / farm_id (plus cell_id, cell_row, cell_col for cell-scoped trees), tree_id / tree_code / tree_version, action_type, severity, confidence, the resolved parameters, actions (four-horizon JSONB), text_en / text_ar, tree_path (the nodes visited), evaluation_snapshot (every value the walk resolved), state, and the timestamps.
recommendations_historyThe state-transition audit log.
tree_parameter_overrides Per-tenant threshold overrides, keyed (tree_id, param_name) with a JSONB value.

evidence and transferability ride inside tree_compiled, so they version immutably with the tree and required no schema change. 5. Anatomy of a tree

A tree is one YAML file. The skeleton, with every optional block shown:

code: potato_petiole_nitrogen_v1        # required, unique, immutable identity
name_en: Potato — petiole sap nitrate  # required
name_ar: البطاطس — نترات عنق الورقة     # optional but expected
description_en: >-                     # optional
  What this tree decides and when it stays silent.
description_ar: >-
  ...

# ---- targeting (all optional; empty = applies to everything) ----
crop_code: potato                      # legacy exact-crop link, resolved to crops.id
crop_paths: [potato]                   # preferred: prefix-matched crop paths
country_codes: [EG]
soil_textures: [sandy, sandy_loam]
applicable_regions: []                 # free-form display metadata

scope: block                           # block (default) | cell

# ---- optional declaration blocks ----
parameters: { ... }                    # tunable numbers, overridable per tenant
evidence: { ... }                      # scientific provenance
transferability: { ... }               # regional suitability grades

# ---- the graph ----
root: root                             # must name a key in nodes
nodes:
  root:                                # a DECISION node
    label_en: Is the block in an interpretable stage?
    label_ar: ...
    condition:
      tree: { ... }                    # see §6
    on_match: next_node_id
    on_miss:  other_node_id

  leaf_example:                        # a LEAF node — has outcome, no condition
    label_en: Deficient — supplement now
    outcome:
      kind: recommendation
      action_type: fertilize
      severity: warning
      confidence: 0.8
      valid_for_hours: 168
      parameters: { priority: high }
      text_en: >-
        What the grower should understand.
      text_ar: >-
        ...
      actions: { ... }                 # see §8

Node rules

  • A node is either a decision (has condition, on_match, on_miss) or a leaf (has outcome). Never both.
  • Every decision node must supply both pointers. There is no implicit fall-through.
  • Every pointer must name an existing node. This is validated at load time, not at run time.
  • label_en / label_ar are what the Conditions tab shows the grower. Write them as questions, because that is how they are rendered.

Scope: block vs cell

A block-scoped tree evaluates once per block, against block-average index values. A cell-scoped tree evaluates once per sub-block grid cell, with that cell's own index means substituted into an otherwise identical context — so it can find a problem affecting one corner of a field. Cell-scoped trees no-op on blocks with no grid, and their recommendations carry cell_id, cell_row and cell_col.

6. The condition language

Each decision node holds a condition.tree: a small recursive JSON/YAML dialect. Two families of node exist.

Boolean nodes — exactly one key

NodeMeaningEmpty list
all_of: [ ... ]AND→ true
any_of: [ ... ]OR→ false
not: { ... }NOT—

Comparison nodes — the op key drives the shape

ShapeNotes
{op: lt|le|gt|ge|eq|ne, left: <ref>, right: <literal|ref>} The six scalar comparisons
{op: between, left: <ref>, low: <…>, high: <…>} Inclusive on both bounds — equivalent to ge low AND le high
{op: in, left: <ref>, values: [ … ]} Set membership; the natural operator for categoricals like growth_stage

left always points at observed data. The literal slots (right, low, high, and entries inside values) may be plain literals or a params reference.

Fail-closed — the single most important rule

Any reference that resolves to None short-circuits its comparison to false. A signal never observed, an index with no scene yet, a growth stage not resolved, a misspelled field name — all behave identically: the comparison is false and the walk takes on_miss.

This is safe, but it is not the same as "no problem". If your on_miss branch leads to a leaf that says "everything is fine", a block with no data at all will be reported as healthy. See the presence-probe pattern in §15.

Malformed conditions are equally permissive: a parse error makes the whole condition evaluate to false rather than raising. Nothing a tree author writes can crash the sweep — but nothing warns you at run time either, which is why the loader validates structure up front and why you should always dry-run.

7. Data sources reference

Every left reference names a source. These are all of them.

indices — per-block satellite indices

{ source: indices, index_code: ndvi, key: baseline_deviation }

Index codes: ndvi, ndwi, evi, savi, ndre, gndvi, ndmi.

keyMeaningType
meanLatest block-average valuenumber
baseline_deviationz-score against the block's own baseline — the defaultnumber
slopeLeast-squares trend over the last 30 days, in index units per daynumber
deltaLast minus first across that 30-day window — total changenumber
trend_directionrising / falling / stable, using a ±0.02 dead-band on deltastring

Trend features are computed at context load from recent aggregate history — there is no trend table and no sweep. Fewer than two cloud-free observations in the window leaves all three None, so trend rules fail closed. Values are quantized to 4 decimal places.

block — attributes of the block itself

{ source: block, field: growth_stage }
fieldMeaning
crop_categoryBroad crop grouping
growth_stageCurrent phenological stage, auto-advanced daily from the crop taxonomy
crop_pathFull hierarchical path, e.g. mango.alphonso.short
crop_strainJust the strain leaf, e.g. short
soil_textureFrom the closed soil vocabulary
salinity_classBlock salinity banding
canopy_size_classResolved size class of the current crop

All categorical — compare with eq, ne, in.

weather — raw farm weather snapshot

{ source: weather, scope: forecast_24h, field: precipitation_mm_total }
scopeTypical fields
latest_observationair_temp_c, humidity_pct, precipitation_mm, wind_speed_m_s, et0_mm
forecast_24h / forecast_72hprecipitation_mm_total, precipitation_probability_pct_max, air_temp_c_max, air_temp_c_min, et0_mm_total
derived_today / derived_yesterdayprecip_mm_7d, gdd_cumulative_base10_season, temp_max_c
Not validated

field is the one string in the whole dialect that is not checked against a closed list — the weather loader is the source of truth for which fields each scope carries. A typo resolves to None and silently fails closed. Verify weather field names with a dry-run.

weather_index — farm-level curated weather indices

{ source: weather_index, index_code: temperature, key: baseline_deviation }

key is value or baseline_deviation (the default) — a z-score against the farm's day-of-year climatology. This is the anomaly-aware counterpart to raw weather: use it for "hotter than this farm's normal for early June", not for "above 35 °C".

weather_risk — per-block disease and pest pressure

{ source: weather_risk, risk_code: powdery_mildew, field: score }

field is score (0–100, the default) or level (low / moderate / high). Unlike weather_index, risk folds in the block's crop and growth stage, so it varies block to block even on one farm.

signals — tenant-defined field observations

{ source: signals, code: petiole_no3n, key: value_numeric }
keyUse for
value_numericNumeric readings — the default
value_categoricalEnumerated observations
value_eventEvent-type observations
value_booleanYes/no observations
value_slope, value_delta, value_trend_direction Trend over the signal's numeric history — same semantics as index trends

Exactly one value_* is populated, according to the signal definition's kind. Reading the wrong one returns None, which fails closed. code is the tenant's own signal_definitions.code.

grid — sub-block spatial anomaly verdict

{ source: grid, index_code: ndvi, field: flagged_count }

Fields: worst_z, flagged_count, worst_row, worst_col, severity. Present only when the latest scene actually crossed the detection threshold, so absence means "no current anomaly" and fails closed. Valid on left only. Note this source has no trend fields — rate of change is block-level only.

params — the tree's own tunables

{ source: params, name: sufficient_early }

Resolves to the parameter's default, or the tenant's override if one exists. Valid in literal slots only — right, low, high, and inside values. Never on left.

8. Leaves and outcomes

FieldRequiredValues / notes
action_typeyes irrigate, fertilize, spray, scout, harvest_window, prune, other, no_action
text_enyesWhat the grower reads. text_ar optional but expected.
kindnorecommendation (default) or alert
severitynoinfo (default), warning, critical
confidenceno0–1, default 0.5, clamped. Ignored for alerts (forced to 1).
valid_for_hoursnoPositive integer; drives expiry. Non-positive or non-integer values are ignored.
parametersnoFree-form JSON stamped onto the recommendation, e.g. priority. params refs here are substituted to literals before storage.
actionsnoThe four-horizon action plan, below

Four-horizon actions

Prose tells a grower what is happening; the action block tells them what to do and when. All four horizons are optional, and each holds a list of localized items.

actions:
  immediate:                 # do it now
    - text_en: Apply supplemental nitrogen through fertigation.
      text_ar: طبّق نيتروجينًا تكميليًا عبر الريّ بالتسميد.
  short_term:                # days to a couple of weeks
    - text_en: Re-sample petioles 7 days after the application.
      text_ar: أعد أخذ عيّنة أعناق بعد 7 أيام من التطبيق.
  long_term:                 # next season / structural
    - text_en: Review the season's nitrogen budget.
      text_ar: راجع الموازنة النيتروجينية للموسم.
  monitoring:                # what to keep watching
    - text_en: Sample the 4th petiole weekly through bulking.
      text_ar: خذ عيّنة من العنق الرابع أسبوعيًا حتى امتلاء الدرنات.

Silence is a design obligation

Always author the quiet leaves

Every path that should produce nothing needs its own no_action leaf with honest text. Real trees typically carry three: within range, no data on record, and outside the interpretable window. They cost nothing at runtime — but they are what the Conditions tab shows a grower asking "why is there no advice for this block?", and they are how you distinguish "measured and fine" from "never measured".

9. Parameters and tenant overrides

Any threshold a grower might reasonably disagree with should be a parameter, not a hard-coded number. Parameters are declared once and referenced anywhere a literal is allowed.

parameters:
  sufficient_early:
    type: number             # number | integer | boolean | string | enum
    default: 1200            # required, and must fit the declared type
    min: 0                   # optional bounds for numeric types
    max: 5000
    description: >-
      Petiole sap NO3-N (ppm) below which the block is deficient
      during vegetative / tuber initiation.

An enum parameter additionally requires a non-empty values list, and its default must be one of them.

Referenced from a condition:

condition:
  tree:
    op: lt
    left:  { source: signals, code: petiole_no3n, key: value_numeric }
    right: { source: params,  name: sufficient_early }

The loader verifies at compile time that every params reference names a declared parameter, so a typo fails the sync rather than silently resolving to None.

Per-tenant overrides

A tenant can override any declared parameter without forking the tree, via PUT /decision-trees/{code}/parameter-overrides/{param_name}. Resolution order at evaluation time is tenant override → declared default. This is the intended way to localize a threshold that is scientifically sound but regionally calibrated — the cultivar caveat on petiole nitrate is exactly this case.

10. Evidence and provenance

Two optional blocks record why anyone should believe this tree. The evaluator never reads them; they ride inside the compiled tree, version immutably with it, and render in the viewer's Provenance panel.

evidence:
  confidence: high              # very_high | high | medium | low
  notes: >-
    Where the numbers come from, which cultivar or region they were
    established on, and what could make them wrong here.
  citations:
    - source_type: extension    # peer_reviewed | fao | usda | extension | university
                                # research_institution | remote_sensing | government
      title: Potato fertilization on irrigated soils — UMN Extension
      url: https://extension.umn.edu/...
      doi: 10.xxxx/yyyy         # optional
      year: 2021                # optional, integer

transferability:
  egypt: medium                 # very_high | high | medium | low | not_applicable
  middle_east: medium
  global: high
Write the caveats, not just the citation

The notes field is where a future reader learns that a threshold is a Russet Burbank value, or that it is fresh-sap ppm rather than dry-weight percent — the kind of distinction that makes a tree fire constantly when it is misread. A citation proves the number was published; the notes prove you understood what it measures.

11. Authoring a new tree

There are two routes, and the choice is about audience, not difficulty.

Platform seed (YAML in the repo)Tenant tree (UI or API)
Visible toEvery tenantThe authoring tenant only
Authored inbackend/app/modules/recommendations/seeds/*.yaml/decision-trees in the app
Ships viaA pull request; synced to the catalog at app startupSaved immediately, no deploy
Use forAgronomic knowledge that is true for everyoneOne customer's own practice or trial

Route A — a platform seed tree

  1. Decide what the tree refuses to say. Before writing any node, write the no_action leaves: what does "fine" look like, and what does "I have no data" look like? Trees that skip this step are the ones that produce false reassurance.
  2. Establish the thresholds from a primary source — an extension service, FAO, or peer review — and note the units and the cultivar/region they were established on. Do not take numbers from a search summary; units are routinely swapped in secondary sources.
  3. Create seeds/<code>.yaml. The filename should match the code, and the code should carry a version suffix (_v1) so a future incompatible rewrite can coexist.
  4. Write the graph. Conventional order: an applicability gate (right stage, right season), then a presence probe (§15), then the actual thresholds, then leaves.
  5. Make every threshold a parameter with a description and sane bounds.
  6. Fill in evidence and transferability, including the caveats.
  7. Write both languages. name_ar, description_ar, label_ar on every node, text_ar on every leaf, and text_ar on every action item. Arabic is a first-class UI language here, not a translation afterthought.
  8. Start the app. sync_from_disk compiles and upserts every seed at startup; a structural error raises there, with the file path and the specific problem. Re-running with no changes is a no-op.
  9. Dry-run against a real block before opening the PR (§13).

Route B — a tenant tree in the app

  1. Go to Decision trees in the navigation and choose to create one. You need the decision_tree.manage capability — held by TenantOwner and TenantAdmin.
  2. Set identity and targeting in the metadata panel: name and description in both languages, crop paths, countries, soil textures, and scope.
  3. Build the graph in the Visual tab. Switch to the YAML tab at any time for the same tree as text — the two are views of one document, not an import/export.
    On the canvasHow
    Add a nodeAdd it, then choose decision or leaf. A new decision node starts unwired — both pointers must be set before it will compile.
    Delete a nodeDeleting re-points anything that referenced it, so the graph never keeps a dangling pointer.
    Rewire a branchDrag from a node's match/miss handle to the target node.
    Edit a conditionThe structured builder offers only the sources, keys and operators the backend actually accepts, and supports the full nested AST — all_of, any_of, not, between, in.
    Undo / redoAvailable throughout; edits are local until you save.
  4. Dry-run from the workspace against a candidate block and read the resulting path.
  5. Publish the version. Publishing is what makes it live for the sweep.

12. Extending an existing tree

Versions are immutable. Editing a published tree creates a new version; the previous one remains readable, and recommendations already produced keep pointing at the version that produced them (tree_version is stamped on every row). Publishing is a separate, deliberate act.

edit ──▶ POST /decision-trees/{code}/versions        create a new draft version
     ──▶ POST …/versions/{version}:publish           make it the live one
     ──▶ (old versions stay readable forever)

Choosing how to extend

You want to…Do this
Change a threshold for one customerA parameter override — no new version, no fork
Change a threshold for everyoneNew version changing the parameter's default
Add a branch or a new leafNew version; add nodes and re-wire
Narrow who it applies toEdit targeting — then re-check :candidate-blocks, because constrained axes exclude unknown values
Change what a leaf advisesNew version editing text_* and actions
Make an incompatible rewriteA new tree with a bumped code (_v2), and archive the old one
Retire a treeArchive it (DELETE /decision-trees/{code}); restorable via :restore
Adding a node is a compatibility question

Inserting a decision node in the middle of an existing path changes where every block downstream of it lands. Because there is at most one open recommendation per (block, tree), an already-open recommendation from the old version will not be replaced until it is resolved. Expect a mixed population for a while after publishing, and do not read that as a bug.

13. Testing before you ship

ToolWhat it answers
POST /decision-trees/{code}:dry-run "If I ran this tree right now against this block, where would it land?" — full path, no writes
GET /decision-trees/{code}/candidate-blocks "Which blocks does my targeting actually select?" — the check that catches an over-narrow axis
GET /blocks/{block_id}/decision-trees:explain "Why did this block get the advice it got — and why did the other trees stay quiet?" Re-walks every visible tree, including the ones that came out clear and the ones that were not targeted. Requires farm_id as a query parameter.
POST /blocks/{block_id}/recommendations:evaluate Evaluate on demand and actually write results, instead of waiting for the hourly sweep

A checklist worth running

  • Dry-run a block that should fire — confirm the path and the leaf text.
  • Dry-run a block with no data for your key input — confirm it lands on the "no data" leaf, not on "everything is fine".
  • Dry-run a block outside the targeting — confirm it is not a candidate at all.
  • Check the Conditions tab in the block dock reads sensibly to a grower: the labels are questions, and a tree that did not fire reads as clear rather than as a failure.

14. Worked example

A real shipped tree, mango_stress_induction_v1, end to end. The agronomy: during the cool pre-flowering window a well-watered mango canopy tends to push a vegetative flush instead of flowering — and a lost flowering is a lost season. Withholding irrigation in that window pushes floral bud differentiation instead.

Why it is an AND, not a threshold

Water stress alone does not induce flowering. It has to coincide with the cool window — bud dormancy sits around 15 °C and roughly 30 °C suppresses induction. Suspending irrigation at warm temperatures produced only vegetative growth in 'Tommy Atkins'; withholding in the cool season raised flowering by about 20 % and yield by about 17 % in 'Kensington Pride'. So the tree fires only when both hold during pre_flowering.

crop_path: mango

parameters:
  wet_ndmi:          { type: number, default: 0.30 }   # canopy counts as well-watered above this
  cool_induction_c:  { type: number, default: 15.0 }   # cool-night threshold

root: root
nodes:
  root:
    label_en: Is the block in the pre-flowering stage?
    condition:
      tree:
        op: eq
        left:  { source: block, field: growth_stage }
        right: pre_flowering
    on_match: wet_and_cool
    on_miss:  leaf_out_of_window

  wet_and_cool:
    label_en: Is the canopy well-watered while the forecast is cool?
    condition:
      tree:
        all_of:
          - op: gt
            left:  { source: indices, index_code: ndmi, key: mean }
            right: { source: params,  name: wet_ndmi }
          - op: le
            left:  { source: weather, scope: forecast_72h, field: air_temp_c_min }
            right: { source: params,  name: cool_induction_c }
    on_match: leaf_warn            # both true → advise withholding irrigation
    on_miss:  leaf_no_action
Three details worth copying

The index choice is load-bearing. Canopy moisture is read from ndmi (NIR–SWIR, a leaf-water index), not ndwi, which is the McFeeters green–NIR open-water index. They sound interchangeable and are not. Because NDMI needs SWIR, this tree is a Sentinel-2 signal and cannot work on PlanetScope 3 m imagery.

Both thresholds are parameters, so a grower in a different climate can recalibrate without touching the structure.

The stage gate comes first. Checking growth_stage before anything expensive means the tree is silent — and honestly silent, via leaf_out_of_window — for the ten months of the year when the question does not apply.

15. Pitfalls

The false-reassurance path

The most common real defect. Because a missing value fails closed, a block with no observations walks the same on_miss route as a block that was measured and found healthy — and lands on your "within range" leaf.

The fix is a presence probe: before comparing against a threshold, test that the value exists at all. For a strictly positive quantity, > 0 is enough:

data_check:
  label_en: Is there a petiole sap nitrate reading for this block?
  condition:
    tree:
      op: gt
      left:  { source: signals, code: petiole_no3n, key: value_numeric }
      right: 0
  on_match: stage_early        # we have data → evaluate it
  on_miss:  leaf_no_data       # we do NOT have data → say so honestly

A one-sided bound on a trend also matches collapse

delta < 0.01 is true for a stalled crop — and equally true for one crashing at −0.4. If you mean stagnant, you want a band, not a bound:

op: between
left: { source: indices, index_code: ndvi, key: delta }
low: -0.01
high: 0.01

Or simply trend_direction eq stable, which has the noise floor built in.

Confusing slope with delta

slope is per day; delta is the total change across the 30-day window. A threshold that is sensible for one is off by roughly 30× for the other.

Assuming mean when you want the anomaly

For both indices and weather_index, the default key is baseline_deviation — a z-score, not a raw value. This is deliberate: an NDVI of 0.4 means nothing without knowing what that block normally does in that week. Write key: mean explicitly when you genuinely want the absolute number.

Prefix matching is wider than it looks

crop_paths: [mango] targets every mango variety and strain. To target one variety, give the fuller path.

Untranslated leaves

text_ar and label_ar are optional to the compiler and mandatory in practice. A missing Arabic string does not fail the sync; it just degrades the Arabic UI at the exact moment a grower needs it.

Both pointers are mandatory

There is no default branch. A decision node missing on_miss ends evaluation with an error rather than falling through to a leaf.

16. Permissions

CapabilityGrantsTypical roles
decision_tree.manage Create, edit, version, publish and archive trees; manage parameter overrides TenantOwner · TenantAdmin · PlatformAdmin
decision_tree.read View the catalog and published trees; dry-run; trigger evaluation the above + PlatformSupport (read-only)
recommendation.read See the recommendations list, the board rail, and the block dock's Conditions tab Agronomist · FarmManager · FieldOperator · Scout · Viewer
recommendation.act Apply / dismiss / defer / schedule recommendations Agronomist · FarmManager

The whole authoring surface is gated on decision_tree.manage: without it the New tree action is hidden and the pages render read-only. Capability checks live on each page, so a deep link with the wrong role still fails rather than rendering.

Field roles can read the reasoning, not the rules

decision_tree.read is deliberately narrow — it also gates :evaluate and :dry-run, both of which can write. So the "why did this fire?" surface (:explain, the Conditions tab) is gated on recommendation.read instead, which every field role holds. An Agronomist can therefore see exactly which conditions were evaluated on their block without being able to author or run trees.
